Package tests execute the real maintenance hooks against isolated old helper and systemctl fixtures, for muted and audible simulated states. They verify that installation does not start RTP, upgrades and removals drain first, interrupted restoration returns failure, and the helper and recovery journal remain available for retry. They do not simulate kernel scheduling, physical ALSA release timing or all distribution package manager behavior. The receiver's cgroup binding and `ExecStopPost` are structurally validated; physical broker crash and package action exercises are still required.

The 50 ms monitor cadence, 250 ms loss threshold, further 250 ms mute deadline, one second unconfirmed UI, three second control/app heartbeat deadlines and 12 second lease are implemented. Unit tests validate their decisions and local control interruption paths. They are not measurements of worst case Pi response under load. The new ingress filter's overhead has not been calibrated acoustically.

Release acceptance remains **outstanding**. Fresh comparable local, Snapcast and filtered RTP measurements must establish median added delay at most 30 ms and p95 at most 50 ms, with calibrated uncertainty. Measure physical picture to sound offset, check for audible glitches and growing delay, run ten minute 20/15/10 ms candidates and 30/40 ms fallback if needed, exercise failures and package actions on the physical receiver, and complete two hours of live F1. Earlier screen capture offsets and the quiet clip's 80% calibration do not establish these results. Software completion authorizes the opt in feature only.

## Pulse bridge scheduling, 2026-09-22

Receiver 1.3.0 adds `libpipewire-module-rt` with `rt.prio = 82` to the private Pulse bridge. The HiFiBerry hardware graph uses FIFO priority 83, but the old bridge used ordinary scheduling. During Spotify Connect playback, the bridge node waited up to 2.839 ms before processing against a 2.667 ms graph cycle. A 90 second baseline recorded four output XRuns and nine bridge node XRuns. Giving the bridge data thread FIFO priority 82 produced no XRuns in the next 90 seconds, with maximum wait 0.081 ms. A restored priority run had no XRuns but again reached 2.033 ms wait, so the short comparison does not establish elimination of every intermittent fault.

The package regression failed against the old configuration, then passed after the change. It reads the built Debian package through PipeWire's configuration parser and verifies that the real time priority fits the installed service limit. The shared signal check also verifies that the actual Pulse process loads the real time module. The full audio gate passed at `build/audio-gate/20260922T152836647701Z/report.json`: 113 Flutter tests, analysis, 71 receiver tests, measurement and routing checks, 79 server tests, and the isolated shared output signal check.

A fresh isolated Pulse bridge on the physical HiFiBerry, using the new configuration and the service's priority limit, acquired `SCHED_FIFO | SCHED_RESET_ON_FORK` at priority 82. The installed and active session templates were updated with backups under `/var/backups/syren-rtp/20260922T173136-priority`, and the existing bridge data thread received the same scheduling policy without restarting playback. This was a configuration update to the installed 1.2.0 package, not a package manager upgrade. The separately built `build/debian/syren-rtp-receiver_1.3.0_all.deb` contains the fix for future installations. The app source version advances to 1.5.0 under the repository version policy; the running desktop app was not replaced.

Longer physical playback acceptance remains separate from the software gate. Deployment and profiler evidence is retained in `/home/yme/desktop-memory-investigation`.

After deployment, five minutes of continuing Spotify Connect playback produced zero new output or follower XRuns across 112,500 profiled cycles. The output counter remained at 53, after having risen from 33 to 53 between the earlier comparison and deployment. The bridge node maximum scheduling wait was 0.113 ms, and the hardware graph maximum wait was 0.235 ms. This is a short live stability check, not the outstanding longer acoustic acceptance test. Evidence: `/home/yme/desktop-memory-investigation/syren-priority-after-fix-2026-09-22.json`.
